# NITEOS Hunt V5 — финальный прототип

## Цель

Система ищет не просто юрлица, а **реальные здания, которые видны с дороги и подходят под архитектурную подсветку**, затем связывает их с кадастром, собственником, предприятием, техническими ЛПР и только после этого показывает тех людей, у кого найден подтверждённый публичный канал связи.

## Пользовательский сценарий

Ввод:

```text
Казань
производственные предприятия
20 объектов
```

Конвейер:

```text
карты/геопоиск
→ кандидаты зданий
→ фасад/панорама/фото
→ lighting score
→ кадастр конкретного здания
→ собственник здания
→ юрлицо/ИНН/ОГРН
→ рекурсивная структура владения
→ технические ЛПР
→ public person contact enrichment
→ verification/confidence
→ sales card
→ AI-анализ фасада
→ персональное КП
```

## Главное правило карточки

```text
NO_SOURCE = NO_FACT
NO_ACTIONABLE_CONTACT = HIDE_PERSON
```

Человек без подтверждённого телефона, e-mail, Telegram/VK/LinkedIn или публичного профессионального профиля **не показывается менеджеру в блоке «Кому писать»**. Он может храниться во внутренней БД как кандидат для последующего enrichment.

Общий телефон предприятия не превращается в телефон конкретного человека.

## Что делает обычный код

Без LLM:

- поиск зданий и организаций;
- координаты и нормализация адреса;
- кадастровое сопоставление;
- собственник/ИНН/ОГРН;
- рекурсивный ownership graph;
- вычисление косвенных долей;
- нормализация ФИО/должностей;
- извлечение телефона/e-mail из публичного текста;
- provenance каждого контакта;
- deterministic confidence;
- фильтрация людей без контактов;
- дедупликация.

## Где включается ИИ

LLM включается **после фактической сборки карточки**.

1. Vision: оценить фасад по реальному фото/панораме.
2. Source synthesis: помочь сопоставить несколько публичных источников по одному человеку, но не создавать новый факт без URL.
3. Proposal: сформировать 2–3 идеи подсветки и короткое КП.
4. Outreach: сделать сообщение под конкретного ЛПР.

LLM запрещено придумывать кадастр, собственника, ФИО, телефон, e-mail, долю владения или должность.

## Рекомендуемый стек источников

### Геоданные

- **2GIS Places API** — здания, организации, адреса, координаты, ИНН и поиск по географии.
- **Yandex Maps / Panorama API** — интерактивная панорама с улицы и проверка того, что фасад действительно виден с дороги.
- OSM/Nominatim — бесплатный резервный геокодер.

Важно: 2GIS умеет фильтровать объекты по наличию фото, но сами фотографии через Places API не выдаёт. Поэтому visual layer должен хранить отдельный источник изображения/панорамы.

### Кадастр

Адаптер `HttpCadastreProvider` принимает любой легальный provider, который по адресу/координатам отдаёт нормализованные кадастровые данные и правообладателя. Конкретный коммерческий API можно заменить без изменения остальной системы.

### Юрлица

- DaData — быстрый company enrichment по ИНН.
- При необходимости: Контур.Фокус/СПАРК/другой официальный B2B-провайдер через отдельный adapter.

### Поиск контактов человека

- Yandex Search API либо другой search gateway;
- официальный сайт компании;
- PDF/DOC/XLS/PPT из публичного веба;
- отраслевые конференции и каталоги;
- тендерные и закупочные документы;
- публичные профессиональные страницы;
- публичные VK/Telegram/LinkedIn/Сетка, если профиль однозначно связан с человеком.

`PublicPersonContactEnricher` строит отдельные запросы для известного ФИО + компании + должности и извлекает только контакты, реально присутствующие в публичном результате/документе.

## Яндекс в этой архитектуре

Yandex Search API подходит как основной российский search layer: индексирует HTML, PDF, DOC/DOCX, XLS/XLSX, PPT/PPTX и изображения.

Yandex Panorama API — основной слой «что реально видно с дороги».

Yandex Vision OCR — дешёвый специализированный слой для сканов, PDF и изображений, когда текст не извлекается напрямую.

YandexGPT можно использовать как российский LLM fallback для текстовой классификации и генерации КП. Для сложного vision + reasoning в прототипе предпочтён OpenAI, но AI router сделан заменяемым.

## OpenAI

Рекомендуемая модель прототипа: `gpt-5.6-terra`.

Почему: поддерживает image input, structured outputs, Responses API и стоит дешевле Sol при достаточном качестве для одной sales-card.

Текущая официальная цена на сентябрь 2026:

- GPT-5.6 Terra: $2 / 1M input tokens, $12 / 1M output tokens.
- GPT-5.6 Luna: $0.20 / 1M input, $1.20 / 1M output — для дешёвой массовой классификации.
- GPT-5.6 Sol: $4 / 1M input, $20 / 1M output — для сложных случаев.

Практическая схема:

```text
Luna → дешёвый triage / классификация найденных источников
Terra → vision фасада + финальная карточка + КП
Sol → только сложные спорные кейсы
```

## Sales card

Менеджеру показывается только:

```text
[фото фасада]
Название / адрес
Lighting score

Кому писать
- ФИО / должность
- телефон
- e-mail / публичный профиль
- confidence

Идея подсветки
Короткое КП

[Написать] [Создать КП] [В работу] [Источники]
```

Не показывается шум: найденный ЛПР без контакта, десятки отвергнутых источников, промежуточные совпадения.

## Следующий production шаг

Не переписывать приложение. Подключить 4 live provider credentials, затем прогнать одну вертикаль:

```text
Казань → 20 зданий → выбрать 5 лучших фасадов → cadastral owner → 2–4 actionable LPR contacts → КП
```

После этого заменить SQLite на PostgreSQL и BackgroundTasks на Redis/RQ/Celery только когда объём реально потребует очереди.
